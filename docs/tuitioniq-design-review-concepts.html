01
Design Review & Recommendation — July 2026

TuitionIQ
Enterprise Design Direction

TuitionIQ gives private tutors and tuition centres one place to manage student rosters and fee collection. The product logic is strong — clean architecture, audit trails, careful money handling. The presentation layer has not yet caught up: two visual systems coexist, typography is unstyled system default, and the dashboard doesn't surface the product's core promise (who paid, who's due, who's overdue). This deck audits the current UI and proposes a unified, finance-grade design language.

02
Current-state audit

Two design systems are shipping at once

A token system (src/shared/theme/tokens.ts) exists and is well-structured — but its own header admits "existing screens are not mass-refactored." 33 of 54 screen/component files still carry hard-coded hex values. The result is visible drift on the most important surfaces, including the login screen (the first thing every user sees).

InconsistentThree blues, three reds

Primary actions render #0E7EF2 on login but #1D4ED8 in the app; errors appear as #BB1F1C, #B91C1C and token #DC2626. Users won't name it, but they feel it as "unfinished."

DilutedCompeting accent colors

Blue is "primary" and teal is "action" — both used for calls-to-action, sometimes on the same screen (login: blue submit button, teal forgot-password link, kickers in teal). Enterprise products keep one interactive color and reserve green/teal for semantic success ("Paid").

GenericUnstyled typography & brand

One fontFamily reference in the entire app — everything renders in the OS default. Weights jump between 400 and 700 with little 500/600 middle ground. The logo is a stock Ionicons "book" glyph. Nothing says "this is a product I'd pay for."

Missed valueDashboard shows metadata, not money

The dashboard's first card lists Plan / Slug / Created date. For a fee-tracking product the first screen should answer: how much collected this month, what's outstanding, who's overdue. That answer currently lives several taps deep.

IA driftActions promoted to navigation

"Billing," "Payment Tracker," and "Record Payment" are three sibling nav items. Record Payment is a task, not a place — enterprise IA puts it as a primary button inside Billing. Mixed copy ("organisation" vs "organization", "Org settings") adds friction.

SolidWhat's worth keeping

The token file's slate neutrals are tasteful. Card/Button/Badge primitives exist with accessibility roles. The responsive sidebar shell (218px / collapsible / mobile overlay) is the right skeleton. This is a consolidation job, not a rebuild.

03
Proposed direction

"Ledger" — a calm, finance-grade design language

Tutors trust TuitionIQ with money. The design should feel like a well-kept ledger: quiet neutrals, one decisive blue, status color used only for payment state, and numbers set in tabular figures that align in columns. Benchmarks: Stripe Dashboard (restraint + data density), Linear (typography discipline), Xero (money-status semantics).

Color — one accent, semantic status

Keep the existing #1D4ED8 as the only interactive color (cheap migration — it's already the token). Add a navy ink #0B1B3B for brand moments. Demote teal: it becomes the "Paid" semantic only.
